[2026-10-30 체크리스트](DEPLOY_CAE00_2026-10-30.md)까지 먼저 적용하라. 이 문서는 그 뒤다.

## 무엇이 바뀌었나

8세대 폴드는 2026-07 에 둘이 나왔다 — Fold7 의 직접 후속인 **Galaxy Z Fold8 Ultra** 와 넓은 폼팩터의 **Galaxy Z Fold8**.
카탈로그에는 GZF8 하나뿐이라 매처가 'Fold8 Ultra' 도 GZF8 로 이었고, 두 기기의 VOC 가 한 코드로 섞였다.

| 고친 것 | 커밋 |
|---|---|
| 카탈로그 GZF8U(Galaxy Z Fold8 Ultra · 갤럭시 Z 폴드8 울트라, 출시 2026-07-25, 앞 세대 GZF7) — alembic 0045 · 시드 파일. GZF8 의 앞 세대(GZF7)는 그대로 둔다(6절) | `d37c634` |
| 매처 — 'Ultra · 울트라' 가 붙은 표기만 GZF8U. 그냥 'Fold8 · 폴드8' 과 '폴드 와이드' 는 GZF8. 'Fold8 Ultra vs Fold8' 같은 비교글은 둘 다 잇는다. 타사 'vivo X Fold8 Ultra' 는 잡지 않는다 | `d37c634` |
| 온톨로지 — GZF8U 는 8세대 폴드 세대 묶음(GZF8)과 '갤럭시 Z 폴드 전 세대' 시리즈에 든다 | `d37c634` |

이미지 · `.env` 는 바뀌지 않았다. DB 는 카탈로그 행 하나(GZF8U)가 늘고, **지난 글 다시 태깅은 사람이 2절 dry-run 을
본 뒤에만, dev 에서** 한다(3절).

**순서가 중요하다.** 새 코드로 sf-mcp 가 뜨면 'Fold8 Ultra' 질의가 GZF8U 로 풀린다. 다시 태깅이 들어오기 전에는 GZF8U 에
글이 없어(dev 에서 새 코드로 풀어 본 `tagged_count` 0) 그 질의가 비어 보인다. 그래서 sf-mcp 재기동은 다시 태깅이 병합으로
들어온 뒤다(4절). 코드는 지금 받아도 된다 — 떠 있는 인스턴스는 재기동 전까지 옛 코드를 쥐고 있다.

## 1. 카탈로그 행 GZF8U — 병합이 가져온다

dev DB 에는 0045 가 이미 들어가 있다. 병합(`merge-from-drive.sh`)이 products 를 code 로 upsert 하므로 dev 덤프(30분마다)가
한 번 병합되면 cae00 에도 GZF8U 행이 생긴다 — 이미 들어와 있을 수 있다. 기다리지 않으려면 손으로 한 번 병합한다
(`bash scripts/drive-sync/merge-from-drive.sh`, 10-27 문서 2절).

```bash
set -a; source .env; set +a
PGPASSWORD=$POSTGRES_PASSWORD apptainer exec instance://sf_postgres psql -h 127.0.0.1 -p $POSTGRES_PORT -U $POSTGRES_USER -d $POSTGRES_DB -c "
SELECT code, name_en, released_at, predecessor_code FROM products WHERE code IN ('GZF8','GZF8U') ORDER BY code;"
# 기대 2행 — GZF8 | Galaxy Z Fold8 | 2026-07-25 | GZF7  ·  GZF8U | Galaxy Z Fold8 Ultra | 2026-07-25 | GZF7
```

병합을 받지 않는 박스라면 `SF_MIGRATE=1 bash scripts/up.sh` 로 alembic 0045 를 돈다(멱등 — 나중에 병합과 겹쳐도 code 로
한 행이다).

## 2. 다시 태깅 범위 — dry-run (읽기 전용, 사람이 본다)

```bash
set -a; source .env; set +a
DB_URL="postgresql+asyncpg://${POSTGRES_USER}:${POSTGRES_PASSWORD}@${POSTGRES_HOST:-127.0.0.1}:${POSTGRES_PORT}/${POSTGRES_DB}"
time APPTAINERENV_DATABASE_URL="$DB_URL" apptainer exec --bind "$PWD/crawler:/crawler" apptainer/sif/crawler.sif \
  sh -c "cd /crawler && python3 -m scripts.retag_split --from GZF8 --to GZF8U" 2>&1 | grep -v '^INFO:' | head -6
```

`--apply` 가 없으면 DB 에 쓰지 않는다 — 세고, 바뀔 행을 CSV(`crawler/logs/retag-split-GZF8-GZF8U-<날짜>.csv`)로만 남긴다.
GZF8U 행이 아직 없으면 '카탈로그에 없는 코드: GZF8U' 로 멈춘다(1절 먼저).

**dev 실측**(2026-10-30, 2분 9초 — 줄 앞의 시각은 뺐다). cae00 은 dev 덤프를 받으니 거의 같아야 한다(마지막 병합 뒤
dev 가 모은 만큼 차이).

```
=== GZF8 → GZF8U: 후보 47452 · 고침 9680 (apply=False) — logs/retag-split-GZF8-GZF8U-2026-10-30.csv ===
    primary GZF8->GZF8U: 6729       대표가 Ultra 로
    primary GZF8->GZF8: 2159        둘 다 짚은 글 — 대표는 GZF8, GZF8U 링크만 더한다
    primary GS26U->GS26U: 173       다른 제품이 대표 — 대표는 그대로, 링크만(이하 같은 꼴, 합 792)
```

| 활성 글 | 지금(dev) | 적용 뒤 기대 |
|---|---:|---:|
| GZF8 대표 | 43,879 | 37,150 (−6,729) |
| GZF8 링크 | 47,452 | 43,745 (−3,707 — 본문이 Ultra 만 짚는 글) |
| GZF8U 대표 | 0 | 6,729 |
| GZF8U 링크 | 0 | 9,680 (primary 6,729 · mentioned 2,501 · compared 450) |

**표본** — 대표가 GZF8U 로 가는 글 20개의 앞부분.

```bash
CSV=$(ls -t crawler/logs/retag-split-GZF8-GZF8U-*.csv | head -1)
IDS=$(awk -F, 'NR>1 && $4=="GZF8U"{print $1}' "$CSV" | shuf -n 20 | paste -sd,)
PGPASSWORD=$POSTGRES_PASSWORD apptainer exec instance://sf_postgres psql -h 127.0.0.1 -p $POSTGRES_PORT -U $POSTGRES_USER -d $POSTGRES_DB -c "
SELECT id, left(regexp_replace(content_original, '\s+', ' ', 'g'), 140) AS text FROM voc_records WHERE id IN ($IDS);"
```

`$4=="GZF8"` 로 바꾸면 GZF8 이 대표로 남고 GZF8U 링크만 더해지는 비교글을 본다.

dev 표본에서 본 것 — 대표가 GZF8U 로 가는 글은 거의 다 Fold8 Ultra 글이다. 두 기기를 함께 다루는 글타래('… Fold 8 |
Fold 8 Ultra …')의 글은 둘 다 잇는다. 그냥 'Fold8 · 폴드8' 이라고만 쓴 글(GZF8 에 남는 37,150행)은 출시 뒤 표본이 대부분
넓은 폼팩터 이야기(세로로 펴 쓰기 · 화면 돌리기)였고, 일부는 글만으로 어느 쪽인지 갈리지 않는다(6절).

**알린다** — 고침 수 · 표본이 괜찮은지 포털(사용자)에 알린다. 다시 태깅을 쓰는 것은 그 확인 뒤다.

## 3. 다시 태깅 적용 — dev 에서 한다 (cae00 에서는 `--apply` 하지 않는다)

cae00 의 병합은 dev 가 아는 글의 대표(product_id)와 링크를 **dev 와 같게** 맞춘다(dev 가 뗀 링크는 뗀다 —
`merge-from-drive.sh` 머리말). cae00 에서만 고치면 다음 병합이 dev 의 옛 태깅으로 되돌린다. 그래서 2절 확인이 오면 dev 쪽
세션이 원본에 적용하고, 30분 덤프와 cae00 병합으로 들어온다. dev 쪽 순서(참고)는 아래와 같다.

1. dev 수집 worker 재기동 — 그 뒤 새 글은 새 매처로 태깅된다
2. `python3 -m scripts.retag_split --from GZF8 --to GZF8U --apply --log logs/retag-split-GZF8-GZF8U-apply.csv` — 되돌리기 CSV
3. dev sf-mcp 재기동

병합은 dev 덤프에 없는 행(이 서버가 모았거나 병합 뒤 dev 가 지운 글 — 병합 출력의 `dev 덤프에 없는 행`)은 건드리지
않는다. 그 수가 0 이 아니면 4절의 dry-run 다시 돌리기에 남는 고침이 그 글이다 — 그 글만 cae00 에서 2절 명령에
`--apply` 를 붙여 돌린다(이미 나뉜 글은 다시 돌려도 그대로다).

## 4. 들어왔는지 보고 sf-mcp 재기동

dev 적용 뒤 첫 병합이 끝나면(출력의 `voc_records ~…` · `voc_product_links +… -…` 가 수천) 수를 본다.

```bash
PGPASSWORD=$POSTGRES_PASSWORD apptainer exec instance://sf_postgres psql -h 127.0.0.1 -p $POSTGRES_PORT -U $POSTGRES_USER -d $POSTGRES_DB -c "
SELECT p.code,
  (SELECT count(*) FROM voc_records v WHERE v.product_id = p.id AND v.archived_at IS NULL) AS primary_active,
  (SELECT count(*) FROM voc_product_links l JOIN voc_records v ON v.id = l.voc_id
    WHERE l.product_id = p.id AND v.archived_at IS NULL) AS links_active
FROM products p WHERE p.code IN ('GZF8','GZF8U') ORDER BY p.code;"
# 기대 — 2절 표의 '적용 뒤' 언저리(GZF8U 대표 6천여 · 링크 9천여)
```

2절 dry-run 을 한 번 더 돌리면 `고침` 이 0(또는 3절의 cae00 만 가진 글 몇)이어야 한다.

그다음 sf-mcp 만 재기동한다(sf-backend 는 이번에 바뀐 매처 · 온톨로지를 쓰지 않는다). 10-27 문서 1절처럼 워치독 락을 쥔다.

```bash
( exec 9>/tmp/sf-watchdog.lock; flock -w 90 9 && exec -a "watchdog.sh(maint-hold)" sleep 600 ) &
HOLD=$!
apptainer instance stop sf-mcp
for t in $(seq 1 60); do ps -eo args | grep -q "[A]pptainer instance: $(id -un) \[sf-mcp\]" || break; sleep 1; done
bash scripts/up.sh 2>&1 | grep -E "✓|⚠|→ instance|semantic"
kill $HOLD
```

**검증** — `✓ sf-mcp semantic import ok`.

## 6. 남은 것 · 결정 몫

- **GZF8 의 앞 세대** — 지금 GZF7. Fold7 의 직접 후속은 Ultra 라 GZF8U 의 앞 세대도 GZF7 이다. 넓은 폼팩터 GZF8 의 앞
  세대를 비울지는 결함 급등 기준선 · 라이프사이클 비교가 바뀌는 결정이라 사용자 몫으로 남긴다.
- **모델코드 사전** — 8세대 폴드의 모델코드 항목은 아직 GZF8 에 있어, 모델코드로 묻는 질의는 GZF8 로 풀린다. 어느
  모델코드가 Ultra 인지 확인되면 옮긴다(사전 한 줄 + 같은 방식의 다시 태깅).
- **이름만으로 안 갈리는 글** — 그냥 'Fold8 · 폴드8' 이라고 쓴 글은 GZF8 에 남는다. 출시 전(2026-07 이전) 2,177행은 소문
  시기 글이라 어느 기기를 말하는지 글만으로는 모른다. 날짜 · 문맥으로 더 가를지는 결정 몫이다.
