## 1. 재기동 — 이미지가 바뀐 네 인스턴스

up.sh 는 SIF 가 인스턴스보다 새것이면 다시 만든다. 10-23 처럼 하나씩 멈추고 프로세스가 사라진 것을 본 뒤 up.sh.
**워치독 tick(매분) 이 끼어들면 옛 supervisor 의 정리가 새 레지스트리를 지운다**(고아 고리) — 재기동 동안 워치독 락을
쥐어 둔다(보유자 이름에 'watchdog.sh' 가 있으면 tick 이 조용히 넘어간다, 15분 뒤 저절로 풀린다).

```bash
( exec 9>/tmp/sf-watchdog.lock; flock -w 90 9 && exec -a "watchdog.sh(maint-hold)" sleep 900 ) &
HOLD=$!
for i in sf-mcp sf-crawler-beat sf-crawler-worker sf-backend; do
  apptainer instance stop "$i"
  for t in $(seq 1 60); do ps -eo args | grep -q "[A]pptainer instance: $(id -un) \[$i\]" || break; sleep 1; done
done
bash scripts/up.sh 2>&1 | grep -E "✓|⚠|→ instance|semantic"
kill $HOLD
```

**검증**
- `✓ sf-mcp semantic import ok` 줄이 보여야 한다(SG-01 기동 스모크). FAILED 면 줄에 적힌 대로 — 패키지가 없으면 이미지,
  코드 모듈이 없으면 바인드.
- `apptainer instance list` 에 네 인스턴스, 다음 워치독 tick 뒤 `logs/watchdog.log` 에 '고아' 줄이 없어야 한다.
- Redis 가 없으면 ⚠ 상자가 뜬다(SG-06) — 덤프로만 받는 서버면 의도된 상태다(5절).

## 2. 덤프 병합을 한 번 손으로 — 어긋난 id 를 바로잡는다

새 병합의 첫 실행이 예전 병합이 정수 그대로 넣은 행을 제자리로 옮기고, 빠진 카탈로그 행(공식 커뮤니티 앱 ·
GS26 계열 · Fold8/Flip8 …)을 넣고, 링크·결함을 처음 옮긴다. 한 트랜잭션이라 중간에 끊겨도 운영 DB 는 그대로다.
병합 직전 스냅샷도 `backups/sf-db-pre-merge-*.sql.gz` 로 남는다.

```bash
bash scripts/drive-sync/merge-from-drive.sh
```

**기대 출력** — dev 실규모 시험. dev 덤프(123만 행)를 복원한 사본의 카탈로그 code 를 모두 돌려 놓고(모든 글이
엉뚱한 플랫폼·제품을 가리키는 최악의 경우) 링크·결함을 비운 뒤 병합했다.

```
→ 병합(한 트랜잭션 — 카탈로그 code upsert · id 번역 · 링크·결함 · 표본 대조 300)
    ✓ 카탈로그 — platforms +0 ~101 · products +0 ~897 · voc_categories +0 ~0
    ✓ voc_records +0 ~0 · 옛 정수 id 행 제자리로 1229676
    ✓ voc_product_links +535562 ~0 -0
    ✓ voc_defects +113246 ~0 -0
    ✓ 표본 대조 300건 — 제품·본문·링크·결함 일치
    · dev 덤프에 없는 행 0 — 이 서버가 모았거나 병합 뒤 dev 가 지운 글(건드리지 않는다)
→ 미리 계산하는 뷰 다시 채우기
    ✓ category_daily (일반 REFRESH)
    ✓ country_daily … ✓ platform_health
```

cae00 에서는 `platforms +<빠진 수>`(공식 커뮤니티 앱 등)·`products +<빠진 수>`(GS26 계열·Fold8/Flip8 …)가 0 이 아니고,
`제자리로` 수는 정수 id 가 우연히 같은 플랫폼의 글만큼 적다. 시간 — 첫 실행 27분(같은 때 30분 덤프와 시험이 겹친
dev), 그다음부터 6분(대부분 staging 복원, 바뀐 것만 쓴다). 첫 실행이 끝나기 전에 박스의 병합 cron 이 또 불러도
잠금으로 건너뛴다(`· 다른 병합이 … 도는 중`). 옮기는 행은 색인 열이 바뀌어 행마다 전문 색인까지 다시 쓰여 오래 걸린다.

첫 실행은 voc_records 를 거의 다 고쳐 쓴다 — 끝나면 한 번 정리한다.

```bash
PGPASSWORD=$POSTGRES_PASSWORD apptainer exec instance://sf_postgres psql -h 127.0.0.1 -p $POSTGRES_PORT -U $POSTGRES_USER -d $POSTGRES_DB \
  -c "VACUUM (ANALYZE) voc_records;"
```

**검증** — 요청서의 어긋남 넷이 사라졌는지(출처 플랫폼과 저장 플랫폼이 같아야 한다).

```bash
PGPASSWORD=$POSTGRES_PASSWORD apptainer exec instance://sf_postgres psql -h 127.0.0.1 -p $POSTGRES_PORT -U $POSTGRES_USER -d $POSTGRES_DB -c "
SELECT pl.code, count(*) AS rows,
       count(*) FILTER (WHERE v.source_url ILIKE '%' || split_part(regexp_replace(pl.base_url, '^https?://(www\.)?', ''), '/', 1) || '%') AS url_matches
FROM voc_records v JOIN platforms pl ON pl.id = v.platform_id
WHERE pl.code IN ('dcinside','naver_cafe','samsung_community','wpnews','mlbpark','gsmarena','ppomppu','bestbuy')
GROUP BY 1 ORDER BY 1;
SELECT count(*) AS links FROM voc_product_links; SELECT count(*) AS defects FROM voc_defects;"
# 기대: 각 플랫폼 rows ≈ url_matches(출처 주소가 그 플랫폼의 것), links·defects 가 0 이 아니다
```

경고 줄이 나오면 아래처럼 한다.
- `⚠ 옮길 자리에 다른 행이 있어 못 옮긴 옛 행 n` — 같은 글이 두 벌일 수 있다. `/tmp/sf-merge-<DB>.log` 를 dev 에 넘긴다.
- `✗ merge 실패 … 표본 대조 실패` — 번역이 어긋났다는 뜻이고 운영 DB 는 그대로다. 출력과 로그를 dev 에 넘긴다.

## 5. 질문에 대한 답(SG-15 · 16 · 17)

**SG-15 — id 어긋남은 어디서 생겼나.** `scripts/drive-sync/merge-from-drive.sh` 가 dev 덤프의 voc_records 를
platform_id·product_id **정수 그대로** 병합했다. 주석의 가정은 '양쪽 seed 가 같아 id 가 같다' 였는데 틀렸다 — 카탈로그
id 는 설치 순서로 매겨진다. dev 는 seed 뒤 마이그레이션·스크립트로 897·101 이 되었고, 새로 깐 cae00 은 마이그레이션(옛
제품) 뒤 seed 였다. FK 거름은 '그 id 가 있나' 만 봐서 엉뚱한 제품·플랫폼에 조용히 붙었다(dev 의 3 은 GS25U, cae00 의 3 은
2012년 모델). 이제 병합이 code 로 번역하고, 끝에 표본을 code 로 대조해 어긋나면 되돌린다 — 같은 길로 되풀이되지 않는다.

**SG-16 — `/crawler` 바인드와 numpy.** 바인드는 레포 정의다 — `scripts/up.sh` 의 sf-mcp 줄(`--bind "$CRAWLER_DIR:/crawler"`,
9fad381 · 10-17 부터). 박스가 넣을 것은 없다. numpy 만으로는 모자랐다 — 새로 지은 이미지는 판이 풀려 mcp 2.x 가 깔려 서버가 아예
안 떴다. numpy + `mcp<2` + 판 lock + `PYTHONNOUSERSITE=1` 이 함께 들어간 새 이미지를 쓴다(1절 기동 스모크로 확인).

**SG-17 — 덤프로만 받으면 결함·태깅이 오는가.** 이제 온다. 예전 병합은 voc_records·voc_categories 만 옮겨 voc_defects·
voc_product_links 가 cae00 에 0행이었다. 새 병합은 둘 다 옮기고(dev 가 아는 글은 dev 와 같게), voc_records.product_id 와
카탈로그도 code 로 맞춘다. 결함 추출·태깅은 dev(수집 서버)에서 돌고 덤프로 넘어오니 cae00 은 worker·beat 없이 받기만
하면 된다. 그때 cae00 이 따로 할 일은 둘 — 미리 계산하는 뷰는 병합이 채우고, PLM 거울은 `scripts/plm-sync.sh` cron.

## 6. 남은 것 · 결정 몫

- **SG-10 분류 기준** — comparison 이 많은 까닭은 분류기가 모델 이름만 나와도 model_mention 을 붙이며 comparison 에 +1 을
  더하는 규칙이다. 의도된 규칙(시험이 지킨다)이라 이슈 순위에서 빼는 데까지 했다. 규칙을 바꿀지는 방침 결정이다.
- **SG-11 범위** — 본문의 일반 사람 이름은 못 찾는다(개체명 인식 없음 — @·u/ 꼴 계정과 작성자 칸만). 라벨 없는 'R+10자'
  일련번호 꼴은 시계 SKU·펌웨어와 겹쳐 두었다.
- **게이트웨이 HG-06** — 응답에 `error` 키가 있으면 ok=false 로 적는 것은 게이트웨이 몫이다. SignalForge 쪽 get_ontology 는
  이제 numpy 가 있어 error 가 아니다.
- **cae00 수집 방식(OB-06)** — 덤프로만 받기로 정하면 worker·beat 는 띄우지 않아도 된다(up.sh 의 ⚠ 상자는 그때 정상).
