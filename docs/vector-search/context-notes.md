# 시맨틱 검색 2단계 작업 노트 (2026-10-17)

## 자원

- bge-m3 (ollama, 1.2GB, 1024차원, L2 정규화). 첫 pull 은 레지스트리 503 — 재시도로 성공.
- 처리량 — 1요청 64건 165건/초, 4병렬 200건/초(본문 800자). 500자로 줄여도 5% 차이라 800자.
- qwen2.5:7b 는 원래 있었다(새 다운로드 없음).
- GPU 16GB 중 평상시 3GB. 적재 중 bge-m3+qwen 이 올라가 13.6GB 까지 봤다 — keep_alive 30m 로
  두면 쉬는 동안 내려간다.

## 무엇이 무엇을 잡나 (실측)

| 질의 | 사전(1단계) | 벡터(bge-m3) | LLM(qwen2.5:7b) |
|---|---|---|---|
| 하루를 못 버텨요 배터리 | 배터리(부품)만 | 상위 12건 전부 배터리 수명 글, 0.75~0.79 | — |
| 폰이 손난로 같아요 | 없음 | 실패 — '옛날 핸드폰 같네'(겉모습 '같다')가 1위 | overheat |

벡터는 문자 그대로의 바꿔 말하기에 강하고 은유·특정 용어에 약하다. LLM 은 은유를 개념 키로
옮기는 데 강하다. 그래서 둘 다 쓴다.

## LLM 개념 추론

- 프롬프트 — 증상 키 32개(한/영 라벨) + 헷갈리는 쌍의 설명(SYMPTOM_HINTS) + 예시 8개.
  설명 없이는 '작동 안 함'↔'앱 튕김', '렌즈 안 먼지'↔'깨짐'을 헷갈려 26건 중 22건만 맞혔다.
- 예시와 겹치지 않는 새 표현 홀드아웃 19/19, 평균 151ms(사전이 이미 잡는 3건은 뺐다 —
  LLM 은 사전이 증상을 못 찾을 때만 부른다).
- 응답은 온톨로지 키로만 받는다(없는 키·중복·3개째 버림). temperature 0 + 질의 캐시.
  6초 넘거나 실패하면 빈손 — 검색은 사전·벡터로 계속 간다.

## 벡터

- 저장 — pgvector 가 없고, DB 에 넣으면 30분마다 도는 Drive 백업이 수 GB 씩 무거워진다.
  crawler/data/vectors/bge-m3/ 에 float32 조각(5만 행) + manifest. MCP 는 mmap 으로 읽고
  manifest 가 바뀌면 30초 안에 다시 연다.
- 쓰기 — 커서는 쓴 만큼만 전진, 실패한 묶음 앞에서 멈춘다(649eb0c 의 교훈). 빈 본문은 벡터 없이
  지나간다(아니면 제자리걸음). 쓰기는 파일 잠금으로 하나만 — 전량 적재와 2시간 증분이 겹치면
  증분이 비켜 선다.
- 검색 — 제품 범위가 6만 행 이하면 범위 id 안에서만, 넘으면 전역 상위 300 뒤 SQL 이 거른다.
  유사도는 질의 안의 상대값(1위=1, 300위=0)으로 바꿔 가중 2.0 — 결함 주석(3)보다 낮게.
  유사도 절댓값은 질의마다 분포가 달라(좋은 질의 0.75~0.79 · 실패한 은유 질의 0.75~0.82)
  문턱으로 쓸 수 없었다.
- 벡터로만 걸린 20자 미만 글은 뺀다 — 짧은 댓글이 유사도를 독식했다. 같은 본문(재수집)은 접는다.
- **사전이 질의를 다 설명하면 벡터를 쓰지 않는다.** 'S25 울트라 발열' 에 벡터를 섞으니 251건 →
  499건, 그리고 표기마다 임베딩이 달라 1단계의 "같은 뜻 = 같은 결과" 가 깨졌다. 벡터는 개념이
  없거나, LLM 이 추론했거나, 사전 밖 낱말이 남을 때만 쓴다.

- 전역 검색은 색인 전체를 훑는다 — 38만 행에서 0.1초(첫 호출 0.2초), 100만 행이면 0.3초 안팎.
  MCP 는 비동기 서버 하나라 그동안 다른 요청이 멈추므로 스레드에서 돈다(numpy 는 GIL 을 놓는다).
  범위 검색은 고른 행을 복사하므로(범위 5만 행이면 200MB) 8,192행씩 나눠 읽는다 — 스왑이 꽉 찬
  날(외부 프로세스 39GB)이었다.

## 전량 적재 뒤 새 질의 점검 (2026-10-18)

**적재** — 992,284건, 83분(197건/초), 3.8GB·조각 20개. 커서까지의 활성 비어있지 않은 행과 정확히 같다.

**지연(전체 색인)** — 전역 0.18~0.27초(첫 호출 0.42초), 범위 5만 행 0.06~0.09초. 색인 조각의 차가운
읽기는 6.8GB/s 라 전부 내려가도 0.6초 안팎이다. 벡터는 병목이 아니다.

**SQL 차가운 캐시** — 브랜드·전역 질의('갤럭시가 찜질팩처럼 뜨끈해요')가 처음엔 6~16초, 바로 다시
돌리면 1초. 몇 분 지나면 다시 식는다. 원인은 1단계부터 있던 것 — PG shared_buffers 128MB(기본값)라
거의 전부 OS 페이지 캐시에 기대는데, 스왑이 꽉 차(39/39GB, 외부 프로세스) 캐시가 빠르게 갈린다
(vmstat bi 350~450MB/s, 우리 프로세스가 아니다). 가장 무거운 건 한국어 동의어 가지(ko 원문 부분일치
seq scan, 17만 버퍼). 빼면 안 된다 — 이 가지만 잡는 글이 발열 14.1%·광탈 2.5%(나머지 1% 미만).
JIT 는 40ms 로 무관. 해법은 인프라(shared_buffers 상향 — 스왑이 꽉 찬 지금은 OOM 위험)나 스키마
(한국어 언급 사전 계산 테이블)라 사용자 결정으로 남겼다.

**잔여어 오염 (고침)** — 새 질의에서 남는 말이 순위를 흐렸다.
- '버벅여요' 에서 증상 '버벅' 을 잡으면 '여요' 가 남았다 → 증상·부품·감성 구간은 낱말 끝까지 지운다.
- '폰이' 가 남아 부분일치로 '아이폰이' 글에 가산 → 맨 '폰'(조사 포함)·빈도 부사('자꾸' 등)는 불용어.
- '실패해요' 활용형 그대로는 본문에 거의 없다 → 명사+하다/되다 활용은 명사만.
- 조사 떼기가 '삼성페이'·'디스플레이'·'딜레이' 의 '이', '손난로' 의 '로' 까지 뗐다 → 받침을 본다
  (이/은/을/과/으로 는 받침 뒤, 가/는/를/와/로 는 받침 없는 음절 뒤).
- '삼성페이' 가 브랜드 '삼성' + '페이' 로 갈려 네이버페이 글까지 가산 → 브랜드 합성어는 통째로.

**추론 증상 가중 (고침)** — 계획에 "추론 개념은 사전 개념보다 낮게" 라고 적고 구현하지 않았다.
'삼성페이 결제가 자꾸 실패해요' 에서 LLM 의 '작동 안 함' 이 사전 증상과 같은 무게(3+1.5)로
1.9만 건 아무 '작동 안 함' 글을 올렸다. SI·TSI 로 따로 걸어 절반(1.5·0.75). 삼성페이 실패 글이
상위 3에 들어왔다.

**남은 한계**
- 기능 이름이 주어인 질의('애플페이 안돼요')는 결함 주석(3)이 남는 말(0.75)을 이겨 일반 '작동 안 함'
  글이 위에 온다. 기능 개념(삼성페이·애플페이·삼성헬스·퀵쉐어 …)을 온톨로지에 넣거나 남는 말을
  희소도로 가중해야 한다 — 관련성 평가셋 없이 무게를 바꾸지 않았다.
- 영어 'phone' 은 기기 범위(스마트폰)인데 한국어 '폰' 은 아니다(1단계 설계). '폰' 을 범위로 넣으면
  기기 이름 없는 미태깅 글이 빠진다 — 범위로 볼지 사용자 결정.
