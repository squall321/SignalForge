과제 정보를 받아 온톨로지로 쓰는 사례를 따라, 검색이 사내 식별자를 알아듣게.

1. **모델코드 사전** — `SM-S938B` → Galaxy S25 Ultra. 본문 태깅 길목에도 들어갔다. dev 에서 모델코드가 든 활성 글
   2,715건 중 미태깅 404건에 제품을 채우고 링크 359개를 더했다(되돌리기 로그 `crawler/logs/retag-model-codes-2026-10-23.csv`).
2. **질의 해석** — 'SM-S938B 발열' = 'S25 울트라 발열' = '삼성 S25 울트라 발열'(제품이 함의한 브랜드 말이 남는 말로 남아
   결과가 갈리던 것도 고쳤다). 출시 전 세대 코드(`SM-S958U`)는 그 세대 전부를 범위로.
3. **PLM 거울** — SP 허브 코어 API 에서 과제(`plm_task`)·개발모델(`plm_model`)·프로젝트를 6시간마다 통째로 받아
   **VOC DB 밖** 파일(`crawler/data/plm/sp_mirror.sqlite`)에 둔다. 과제코드·과제명은 사내 정보라 30분 Drive 백업·
   덤프에 싣지 않는다(사용자 결정). 그래서 **cae00 이 허브에서 직접 받아야 한다** — dev 의 거울은 cae00 으로 오지 않는다.
   주소와 토큰이 없으면 아무것도 안 하고(`not_configured`) 과제 검색만 꺼진다.

## 1. 재기동 — sf-mcp · sf-crawler-worker · sf-crawler-beat

질의 해석(sf-mcp), 태깅 길목(worker), 6시간 PLM 받기(beat)가 새 코드를 읽어야 한다. 하나씩 멈추고 up.sh.

```bash
for i in sf-mcp sf-crawler-beat sf-crawler-worker; do
  apptainer instance stop "$i"
  for t in $(seq 1 25); do ps -eo args | grep -q "[A]pptainer instance: $(id -un) \[$i\]" || break; sleep 1; done
done
bash scripts/up.sh
```

**검증** — 모델코드 질의가 제품으로 풀리는지(10-17 문서 1절의 세션 변수 `H`·`SID`·`P` 그대로).

```bash
curl -s "${H[@]}" -H "mcp-session-id: $SID" -X POST "http://127.0.0.1:$P/mcp" \
  -d '{"jsonrpc":"2.0","id":5,"method":"tools/call","params":{"name":"semantic_search","arguments":{"query":"SM-S938B 발열","limit":3}}}' \
  | sed -n 's/^data: //p' \
  | python3 -c "import json,sys; r=json.loads(json.loads(sys.stdin.read())['result']['content'][0]['text']); i=r.get('interpretation',{}); print(r['strategy'], r['total'], [c['key'] for c in i.get('concepts',[]) if c['type']=='product'])"
# 기대: semantic <건수> ['GS25U'] — 'S25 울트라 발열' 과 같은 건수
```

## 2. PLM 거울 켜기 — cae00 에서만

**확인**

```bash
grep '^SF_SP_CORE_URL=' .env; ls -l crawler/data/plm/sp_token 2>&1
```

**조치** — SP 허브 관리자에게 받을 것 둘.
- 허브의 API 루트 주소(끝에 `/api` 까지 — 카탈로그가 `<주소>/core`).
- `core:read` 범위 토큰 — 그 토큰으로 `plm_task`·`plm_model`(·`plm_project`)이 코어로 보여야 한다.

```bash
grep -q '^SF_SP_CORE_URL=' .env \
  && sed -i "s#^SF_SP_CORE_URL=.*#SF_SP_CORE_URL=https://<허브>/api#" .env \
  || echo "SF_SP_CORE_URL=https://<허브>/api" >> .env
mkdir -p crawler/data/plm
umask 077; printf '%s\n' '<core:read 토큰>' > crawler/data/plm/sp_token; chmod 600 crawler/data/plm/sp_token
```

토큰을 `.env` 에 두지 마라 — up.sh 가 .env 전부를 모든 컨테이너 환경으로 내보낸다. `crawler/data/` 는 git·Drive
동기화 밖이다. 주소를 바꿨으면 beat·worker 를 1절처럼 다시 띄운다(.env 는 기동 때 읽는다).

**한 번 바로 받기**(6시간을 기다리지 않는다) — 2026-10-27 고침. 예전 명령은 워커 인스턴스 안에서 돌아 워커가
없거나 .env 를 읽지 않은 셸에서는 `not_configured` 로 끝났다. 이제 스크립트가 .env 를 읽고 이미지로 바로 돈다.

```bash
bash scripts/plm-sync.sh
# 기대: {"status": "ok", "counts": {"plm_project": …, "plm_task": …, "plm_model": …}, …}  종료 코드 0
cat crawler/data/plm/status.json
```

**Redis 가 없는 서버**(beat 의 `plm-sync-6h` 가 돌지 않는다 — cae00) 는 같은 스크립트를 cron 에 건다.
종료 코드는 ok·not_configured 0, held 2, error 1 이다.

```bash
( crontab -l 2>/dev/null; echo "17 */6 * * * bash $PWD/scripts/plm-sync.sh >> $PWD/logs/plm-sync.log 2>&1" ) | crontab -
```

| 결과 | 뜻 | 할 일 |
|---|---|---|
| `not_configured` | 주소나 토큰 파일이 없다 | 위 조치 |
| `error` · `401`/`403` | 토큰이 틀렸거나 `core:read` 가 아니다 | 허브 관리자 |
| `error` · `plm_task 가 없다` | 그 토큰에 과제가 코어로 안 열렸다 | 허브 관리자 |
| `error` · `HTTP 404 … /api 까지인지` | 주소 끝이 틀렸다 | `/api` 까지로 |
| `held` | 한 타입이 지난번의 절반 아래로 줄었다 — 옛 거울을 그대로 둠 | 토큰의 부서·공개 범위가 바뀌었는지 확인. 정말 줄었으면 `bash scripts/plm-sync.sh --allow-drop` |

**검증** — sf-mcp 는 거울 파일이 바뀌면 30초 안에 다시 읽는다(재기동 불필요).

```bash
curl -s "${H[@]}" -H "mcp-session-id: $SID" -X POST "http://127.0.0.1:$P/mcp" \
  -d '{"jsonrpc":"2.0","id":6,"method":"tools/call","params":{"name":"get_ontology","arguments":{}}}' \
  | sed -n 's/^data: //p' | python3 -c "import json,sys; r=json.loads(json.loads(sys.stdin.read())['result']['content'][0]['text']); print(r.get('plm'))"
# 기대: {'active': True, 'tasks': …, 'models': …, 'pulled_at': …}
```

이어서 아는 과제코드 하나로 `semantic_search('<과제코드> 발열')` — `interpretation.notes` 에
"과제 <코드>(<과제명>) → <제품코드>" 가 보여야 한다. "제품에 이어지지 않는다 — 개발모델의 모델코드가 사전에 없다(…)"
가 나오면 그 개발모델의 기본 코드가 모델코드 사전에 없는 것이다(출시 전 신모델 등) — dev 에 알려 사전을 늘린다.
