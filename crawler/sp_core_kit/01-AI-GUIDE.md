# SP 코어 온톨로지 주기 수신 — 구현 지시서

> **이 문서는 AI 코딩 도우미(Claude Code · Cursor · Codex 등)가 읽고 구현하라고 쓴 것입니다.**
> 사람은 `00-START-HERE.md` 를 보십시오. 키트 판 `{KIT_VERSION}`.

## 0. 할 일

이 저장소의 플랫폼에, Standard Platform(이하 **SP**)이 공개하는 **코어 온톨로지**를 **주기적으로
받아 이 플랫폼에 반영하는 기능**을 만든다. 코어 온톨로지는 여러 플랫폼이 함께 쓰는 기준정보
객체(공급사 · 부품 같은 것)와, 그 객체들 사이의 관계(선)다. 선에는 뜻이 붙을 수 있다 — 유효 기간 ·
수량(BOM 의 「몇 개」) · 계보(무엇에서 만들어졌나). 어느 관계 종류가 어떤 뜻을 갖는지는 카탈로그가
말한다(§5.2).

SP 의 코드는 볼 수 없다. 필요한 것은 이 폴더에 다 있다.

| 파일 | 무엇 |
| --- | --- |
| `01-AI-GUIDE.md` | 이 지시서 — 무엇을 만들고 무엇을 지키나 |
| `sp_core_pull.py` | **참고 구현** — 아래 규칙을 모두 지키는 받는 쪽(파이썬 한 파일). 그대로 옮기거나, 다른 언어로 같은 동작을 만든다 |
| `README.md` | 참고 구현 사용법 · 응답 예시 |
| `testbed/fake_sp.py` | **시험장** — 가짜 SP. 실제 SP 와 같은 모양으로 답하고, 단계마다 까다로운 상황을 일으킨다 |
| `testbed/compare.py` | **채점기** — 이 플랫폼이 받은 결과를 시험장의 정답과 비교한다 |
| `testbed/dump_reference.py` | 참고 구현의 결과를 채점기 모양으로 내보내는 예 |
| `check.sh` · `config.example.ini` | 실제 SP 연결 점검 · 참고 구현 설정 |

**이 지시서와 참고 구현이 어긋나면 지시서가 정본이다.** 어긋난 곳은 보고에 적는다.

## 2. 구현 전에 사람에게 물을 것 (한 번에 묻는다)

1. **SP 주소와 토큰.** 주소는 끝이 `/api` 다(예: `https://sp.example.com/api`). 토큰은 SP 담당자가
   발급한다(범위 `core:read`). **토큰은 코드 · 저장소에 넣지 않는다** — 환경변수나 이 플랫폼의 비밀
   저장소에 둔다. 아직 없으면 시험장으로 먼저 만들고 나중에 연결한다.
2. **받을 타입.** 카탈로그(`GET /api/core`)를 읽어 타입 목록(이름 · 건수 · 칸)을 보여 주고 고르게
   한다. 주소 · 토큰이 아직 없으면 시험장의 카탈로그로 모양을 보여 준다.
3. **타입마다 이 플랫폼의 어디에 넣나.** 이미 있는 표 · 화면에 잇나, 새로 만드나. 칸 매핑.
   **관계 종류도 하나씩 묻는다** — 카탈로그의 `relation_kinds` 를 보여 주고 종류마다 고르게 한다.
   - 어디에: 이 플랫폼의 연결 표에 넣나 · 레코드 화면에 「관련 항목」 으로 보이기만 하나 · 안 받나.
     같은 상대라도 참조 칸(예: 「주 공급사」)과 관계(`supplied_by`)는 따로 온다 — 하나로 합칠지도 묻는다.
   - 뜻을 쓰나: 수량 칸(`quantity_key`)이 있는 종류는 수량을 보일지 · 전개(경로 따라 곱하기)를 할지,
     계보 관계(`lineage_source`)는 「무엇에서 만들어졌나」 를 보일지, 유효 기간(`effectivity`)이 있는
     종류는 끝날을 보일지.
4. **SP 에서 사라진 것**(지움 · 합침 · 안 보이게 됨)을 이 플랫폼에서 어떻게 보이나.
   기본 제안: 지우지 않고 「사용 안 함」 으로 둔다. 새로 고르는 목록에서는 숨기고, 이미 쓴 기록에서는
   이름을 그대로 보인다. 함께 물을 것:
   - **그만 씀**(`status: deprecated` — 사라진 것이 아니라 새로 쓰지 말라는 것). 기본 제안: 새로
     고르는 목록에서만 숨기고 「사용 안 함」 과 구별해 표시한다.
   - **합쳐졌을 때**(`merged_into`) 이 플랫폼의 참조를 이긴 쪽으로 옮기나 — 그 참조를 쥔 레코드가
     **사람이 이 플랫폼에서 만든 것**이어도 옮기나.
5. **이 플랫폼에서 사람이 고친 값과 SP 값이 다르면.** 기본 제안: SP 가 정본이다(덮어쓴다).
   SP 에서 온 칸은 이 플랫폼 화면에서 읽기 전용으로 둔다. 함께 물을 것: SP 는 **안 보이게 된 대상을
   가리키는 참조 칸을 빼고 보낸다** — 「SP 가 정본」 이면 그 참조가 비게 된다. 이미 쓴 기록을 지키려면
   「대상이 사라져 빠진 참조는 비우지 않는다」 로 정할 수 있다.
6. **주기.** 기본 제안: 매일 03:00 한 번, 「지금 받기」 버튼, 주 1회 「처음부터 다시 받기」.
7. **「확인 필요」 를 누구에게 어떻게 알리나**(화면 표시 · 메일 · 메신저).
8. **이미 이 플랫폼에 같은 것이 있나**(사람이 먼저 만든 공급사 등). 있으면 처음 한 번 잇는 방법을
   정한다 — 기본 제안: 이름이 같은 후보를 목록으로 보여 주고 사람이 고른 것만 SP key 를 채운다.
   이름으로 저절로 잇지 않는다.

3 ~ 5 의 답을 받기 전에 짐작으로 만들지 않는다. 층 1(§4 · §5)은 답과 상관없으니 먼저 만들어도 된다.

## 3. 구조 — 반드시 두 층으로 나눈다

```
SP ──HTTP──▶ [층 1  받기] ──▶ 사본 표 ──▶ [층 2  반영] ──▶ 이 플랫폼의 표 · 화면
             SP 규칙만 안다              매핑만 안다
```

- **층 1(받기)** 은 SP 가 준 것을 **있는 그대로** 사본 표에 맞춘다. 이 플랫폼의 표를 모른다.
- **층 2(반영)** 는 사본 표만 읽는다. SP API 를 부르지 않는다.
- **둘을 섞지 않는다.** §5 의 규칙이 매핑 코드 사이로 흩어지면 반드시 하나가 빠진다(실제로 그랬다).
  나눠 두면 규칙이 한 곳에 모이고, 시험장이 층 1 을 채점하고, SP 쪽이 바뀌어도 층 1 만 고친다.

이 플랫폼이 파이썬이면 `sp_core_pull.py` 를 층 1 로 그대로 써도 된다. 그때 사본은
`out/sp_core.sqlite` 이고, 표 모양은 `README.md` 에 있다. 그래도 층 2 · 화면 · 주기 · 자동 시험은
만든다. 다른 언어면 같은 동작을 옮긴다 — 함수 이름도 대응시켜 두면 나중에 대조하기 쉽다.

## 4. 사본 표 (층 1 이 가진다)

이름은 이 플랫폼의 관례를 따라도 된다. **칸의 뜻은 바꾸지 않는다.**

| 표 | 칸 | 키 |
| --- | --- | --- |
| `sp_core_object` | `type_slug` · `key` · `label` · `status` · `properties`(JSON) · `active` · `merged_into` · `sp_updated_at` · `changed_at` | (`type_slug`, `key`) |
| `sp_core_relation` | `src_type` · `src` · `relation` · `dst` · `dst_type` · `properties`(JSON) · `evidence_note` · `active` · `sp_updated_at` · `changed_at` | (`src_type`, `src`, `relation`, `dst`, `dst_type`) |
| `sp_core_previous_key` | `type_slug` · `old_key` · `key` | (`type_slug`, `old_key`) |
| `sp_core_sync_state` | `stream`(`<타입>` 또는 `<타입>#relations`) · `since`(받은 `as_of` 문자열 그대로) | `stream` |
| `sp_core_catalog` | `revision` · `body`(JSON) · `received_at` — 직전 것을 남긴다 | |
| `sp_core_run` | `started_at` · `finished_at` · `mode`(보통 · 처음부터) · `result`(정상 · 확인 필요 · 실패) · `counts`(JSON) · `problems`(확인 필요 사유) · `notes`(정의 판 바뀜 같은 알림) · `error` | |

- `changed_at` 은 **이쪽 시각**이다 — 층 1 이 그 행의 값을 **실제로** 바꾼 때. 같은 값이 다시 오면
  그대로 둔다. 비활성으로 돌림 · key 옮김 · 선 끊기도 바꾼 것이다. 층 2 는 이것으로 「지난 반영 뒤에
  바뀐 것」 을 고른다.
- SQL 마이그레이션이 없는 플랫폼(파일 DB 등)이면 그 플랫폼의 스키마 변경 방식을 따른다.
- 끊은 선은 `active=false` 로 두거나 지운다. 둘 중 하나로 정하고 일관되게 한다.
- **관계 종류의 뜻은 `sp_core_catalog.body` 에 있다**(`types[].relation_kinds[]` — 끝에 설 수 있는
  타입 · 유효 기간 · 수량 칸 · 계보의 원천 끝). 층 2 는 그것을 읽는다. 따로 표로 풀지 않아도 된다.
- 선의 `valid_from` · `valid_to`(유효 기간)는 **선택**이다. 층 2 가 「언제까지」 를 보이려면
  `sp_core_relation` 에 두 칸을 더한다. SP 는 오늘 유효한 선만 보내고 끝나는 날 끊김을 보낸다 — 그래서
  두 칸이 없어도 사본의 상태는 맞다. 참고 구현은 두 칸을 두지 않는다.

## 5. 받기 (층 1)

### 5.1 한 번 실행의 순서

1. **잠금.** 이미 돌고 있으면 시작하지 않는다(주기 실행과 버튼이 겹친다). 둘이 다른 프로세스에서
   돌 수 있으면 프로세스 사이 잠금(DB 행 잠금 · 잠금 파일)으로 한다.
2. **카탈로그.** `GET /api/core`. 직전 카탈로그와 `revision` 이 다르면, 달라진 점(타입 · 칸 · 관계)을
   실행 기록에 남기고 **모든 흐름의 `since` 를 비운다**(처음부터 받는다).
3. **객체.** 받을 타입마다 객체 흐름을 받는다(§5.3).
4. **선.** 객체를 **모두** 받은 뒤, 카탈로그의 `types[].relations` 가 비지 않은 타입마다 선 흐름을 받는다.
5. **결과.** 실행 기록에 결과(정상 · 확인 필요 · 실패) · 건수 · 사유를 남긴다. 확인 필요 · 실패면 알린다.

### 5.2 API

모든 요청에 `Authorization: Bearer <토큰>` 을 붙인다. 응답은 JSON 이다.

| 호출 | 무엇 |
| --- | --- |
| `GET /api/core` | 카탈로그 — 공개 타입, 칸, 관계 종류, 정의 판(`revision`) |
| `GET /api/core/<타입>?since=&cursor=&limit=` | 객체 한 쪽 |
| `GET /api/core/<타입>/relations?since=&cursor=&limit=` | 그 타입에서 **출발하는** 선 한 쪽 |

- `limit` 은 1 ~ 2000(기본 500). `since` 를 빼면 처음부터 전량이다. `cursor` 는 지난 응답의 `next` 를
  **그대로** 넣는다(모양은 약속이 아니다). 끝 슬래시(`/api/core/`)도 같은 응답이다.
- 오류는 `{"error": {"code": "...", "message": "..."}}` 이다. **코드의 끝**으로 가른다(접두사는 설치마다
  다를 수 있다).

카탈로그(줄임):

```json
{ "system": "standardplatform", "revision": "3-0481920033", "as_of": "2026-09-22T02:00:00.000000Z",
  "shapes": ["core", "sp"],
  "types": [
    { "slug": "part", "label": "부품", "description": "", "count": 1240,
      "updated_at": "2026-09-21T08:11:00.123456Z",
      "endpoint": "https://sp.example.com/api/core/part",
      "relations_endpoint": "https://sp.example.com/api/core/part/relations",
      "relations": ["supplied_by", "contains"],
      "relation_kinds": [
        { "slug": "supplied_by", "label": "공급처",
          "src": [{ "slug": "part", "interface": false, "types": ["part"] }],
          "dst": [{ "slug": "vendor", "interface": false, "types": ["vendor"] }],
          "effectivity": true, "quantity_key": "", "lineage_source": "" },
        { "slug": "contains", "label": "구성품",
          "src": [{ "slug": "part", "interface": false, "types": ["part"] }],
          "dst": [{ "slug": "part", "interface": false, "types": ["part"] }],
          "effectivity": false, "quantity_key": "qty", "lineage_source": "" } ],
      "properties": [
        { "key": "weight", "label": "무게", "data_type": "number", "unit": "kg" },
        { "key": "vendor", "label": "주 공급사", "data_type": "object_ref", "ref_type_slug": "vendor", "multi": false },
        { "key": "tags", "label": "꼬리표", "data_type": "text", "multi": true } ] } ] }
```

관계 종류의 끝(`src` · `dst`)에는 타입이나 **인터페이스**(여러 타입이 따르는 공통 모양)가 적힌다.
`types` 가 그 끝에 설 수 있는 공개 타입이다. 뒤의 세 칸이 선의 뜻이다.

| 칸 | 뜻 | 비면 |
| --- | --- | --- |
| `effectivity` | 참이면 선마다 유효 기간(`valid_from` · `valid_to`)이 실린다 | 거짓 — 기간 없음 |
| `quantity_key` | 선의 `properties` 중 「부모 하나에 자식 몇 개」 인 숫자 칸의 **키** | 빈 문자열 — 수량 없음 |
| `lineage_source` | 계보 관계면 원천(만드는 데 쓰인 것) 끝 — `src` 또는 `dst` | 빈 문자열 — 계보 아님 |

받기(층 1)는 이 셋과 상관없이 같다. 쓰는 쪽은 층 2 다(§6.2).

객체 한 쪽 — **봉투의 칸은 늘 같다**(값이 없으면 `null` · `false` · `[]`):

    { "key": "V-3", "label": "ACME Inc.", "status": "active", "updated_at": "…",
      "deleted": true, "hidden": false, "merged_into": "V-1", "renamed_from": null, "previous_keys": [],

    { "key": "V-6", "label": "V-6", "status": "active", "updated_at": "…",

선 한 쪽 — 같은 규칙. 너무 오래 안 받았으면 `reset` 이 온다:

```json
{ "type_slug": "part", "as_of": "…", "next": null, "reset": false, "reset_reason": "",
  "items": [
    { "src": "P-1", "relation": "supplied_by", "dst": "V-1", "dst_type": "vendor",
      "evidence_note": "", "properties": { "n": 3 }, "valid_from": "2026-01-01", "valid_to": "2027-01-01",
      "updated_at": "…", "deleted": false, "periods": null },
    { "src": "P-1", "relation": "contains", "dst": "P-7", "dst_type": "part",
      "evidence_note": "", "properties": { "qty": 4 }, "valid_from": null, "valid_to": null,
      "updated_at": "…", "deleted": false },
    { "src": "P-5", "relation": "supplied_by", "dst": "V-2", "dst_type": "vendor",
      "evidence_note": "", "properties": {}, "valid_from": null, "valid_to": null,
      "updated_at": "…", "deleted": true } ] }

{ "type_slug": "part", "as_of": null, "next": null, "items": [], "reset": true,
  "reset_reason": "90일보다 오래된 시점부터는 끊긴 선을 알려 줄 수 없습니다 — `since` 를 비우고 처음부터 받으세요." }
```

값의 표기: 참조 칸(`object_ref`)은 상대 객체의 `key`(선에 붙은 참조 칸도), 여러 값은 배열, 날짜 `2026-09-22`,
일시 `2026-09-22T01:23:45.000000Z`. **빈 값은 칸이 아예 없다.** 별칭이 있으면 `properties.aliases` 에 배열로 온다.
`shapes` · `extra` · `periods` 는 SP 끼리 받는 모양(`shape=sp`)의 것이다 — 이 키트는 쓰지 않는다(`extra` ·
`periods` 는 늘 `null`).

### 5.3 한 흐름 받기

흐름은 「타입 하나의 객체」 또는 「타입 하나의 선」 이다. 기준 시각은 흐름마다 따로 둔다.

```
since = state[흐름]                       # 없으면 "" — 처음부터
full = (since == "")
cursor = 없음 ; seen = {} ; 다시받음 = 거짓 ; reset받음 = 거짓
반복:
    res = GET 주소?limit=500 [&since=since] [&cursor=cursor]
        404 · 코드 끝 -CORE-0002 → cursor 가 있었고 아직 안 했으면: cursor = 없음 ; 다시받음 = 참 ; 계속
                                   아니면: 실패
        404 · 코드 끝 -CORE-0001 → 이 타입은 건너뛴다 · 확인 필요 · 다음 타입으로
    res.reset 이 참 → 이미 한 번 받았으면 실패(「since 를 비웠는데도 reset」)
                      아니면: since = "" ; full = 참 ; cursor = 없음 ; reset받음 = 참 ; 계속
    res.items 적용 (§5.4)
    seen += 이번 쪽의 deleted 아닌 것들의 키
    cursor = res.next
    cursor 가 있으면 계속
    full 이면 부재 대조 (§5.5)
    state[흐름] = res.as_of                 # 문자열 그대로. 이때만 저장한다
    끝
```

쪽마다 커밋해도 된다 — 같은 행이 두 번 와도 덮어쓰면 그만이다. **기준 시각만** 마지막 쪽 뒤에 저장한다.
커서를 버리고 다시 받거나 `reset` 으로 처음부터 받을 때 `seen` 은 비워도, 그대로 둬도 결과가 같다.

### 5.4 행 적용

**객체** — 차례대로 한다.

1. **옛 식별자.** `previous_keys`(옛 식별자 전부, 오래된 것부터)와 `renamed_from`(마지막 옛 식별자)
   중 하나라도 가진 행(같은 타입)이 있으면, 그 행의 `key` 를 새 것으로 바꾼다. 새 `key` 행이 이미
   있으면 옛 행은 지운다(같은 것의 두 번째 줄이다). 선의 끝도 옮긴다 — `src_type`=그 타입이고
   `src`=옛 key 인 것, `dst_type`=그 타입이고 `dst`=옛 key 인 것. `sp_core_previous_key` 에
   (타입, 옛 key) → 새 key 를 **모두** 적는다.
2. **`hidden: true`** — 지운 것이 아니라 이 토큰으로 더 이상 안 보이게 된 것이다. 가진 행이 있으면
   `active=false` 만 한다 — **이름 · 칸은 덮지 않는다**(오는 이름은 식별자고 칸은 비어 있다).
   가진 행이 없으면 아무것도 만들지 않는다.
3. **`deleted: true`** — `active=false`, `merged_into` 를 적는다. 지우지 않는다. `label` · `status` 는
   받은 대로 두고, `properties` 는 **가진 것을 그대로 둔다**(빈 채로 온다 — 덮으면 이미 쓴 기록이 보일
   값이 사라진다). 가진 행이 없으면 비활성 행으로 만든다(`merged_into` 를 남기려고).
4. **그 밖** — upsert. `label` · `status`(`active` · `deprecated`) · `properties` 를 **통째로 바꾸고**
   `active=true`. 기존 칸에 합치면 SP 에서 비운 칸이 안 지워진다.
5. **되살림** — 비활성이던 (타입, key) 가 `deleted: false` 로 오면 다시 활성이다. 이때 **모든 선 흐름의
   `since` 를 비운다** — 그 객체의 선은 바뀐 것이 아니라서 증분으로 다시 오지 않는다.
6. **사라진 것의 선** — 2 · 3 이면 그 객체를 끝으로 하는 선을 모두 끊는다. 출발 쪽은
   (`src_type`, `src`), 도착 쪽은 (`dst_type`, `dst`) 로 찾는다. SP 는 지운 객체의 선을 **「끊긴 선」 으로
   보내지 않는다**(합치기도 같다 — 진 쪽의 선은 이긴 쪽으로 옮겨 새로 오고, 옛 선의 끊김은 안 온다).

**선**

- `deleted: true` — 그 다섯 칸의 선을 끊는다.
- 그 밖 — upsert. 단 **도착 객체가 사본에서 비활성이면 넣지 않는다.**
- 선의 키는 **다섯 칸**이다(`src_type`, `src`, `relation`, `dst`, `dst_type`). `key` 는 타입 안에서만
  하나라, 끝이 인터페이스인 관계는 같은 `dst` 가 두 타입에 있다.
- `valid_from` · `valid_to`(있을 수 있다) — 그 선의 **유효 기간**(시작일 포함 · 끝날 제외,
  `YYYY-MM-DD`). 카탈로그의 `relation_kinds[].effectivity` 가 참인 종류만 채워 온다. SP 는 **오늘 유효한
  선만** 보내고, 끝날이 지나면 그 선을 `deleted: true` 로 알린다(같은 두 객체 사이의 다음 기간 선이
  그날 시작하면 그 선으로 바꿔 보낸다) — 그래서 선의 키는 그대로 다섯 칸이고, 받는 쪽은 이 두 칸을
  저장만 해도(또는 버려도) 된다. 지난 기간 선을 고치거나 앞으로의 선을 만든 일도 흐름에 들지만, 늘 **그
  선의 오늘 상태**(오늘 유효한 같은 선, 없으면 끊김)로 온다.
- 카탈로그의 `relation_kinds[].quantity_key` · `lineage_source`(§5.2) — 선의 모양은 그대로라 받기는 할
  일이 없다. `properties` 를 통째로 담아 두면 층 2 가 쓴다(§6.2).

### 5.5 처음부터 받았을 때 — 부재 대조

`since` 없이 받으면 지워진 것은 오지 않는다. 그래서 「지워졌다」 는 부재로만 안다.

- **마지막 쪽까지 받은 뒤에만** 한다. 그 흐름의 활성 행 중 이번에 안 온 것을 객체는 비활성으로
  돌리고(그 선도 끊는다, §5.4-6), 선은 끊는다. **먼저 비우지 않는다** — 받다가 끊기면 아직 안 받은
  것까지 사라진다.
- **안전장치.** 안 온 것이 10건을 넘고 가진 활성의 절반을 넘으면 정리하지 않는다. 결과는 「확인
  필요」 다(공개 측이 한꺼번에 많이 지웠거나, 토큰으로 볼 수 있는 범위가 줄었을 수 있다 — 공개 측이
  조회를 부서별로 좁힌 설치에서 토큰 주인의 소속이 바뀐 경우). 받은 것은 반영하고 기준 시각도 옮긴다.
  사람이 확인한 뒤 「강제 정리」 로만 적용한다(참고 구현의 `--allow-shrink`).

### 5.7 이 창구로 오지 않는 것

사람이 아래 것을 원하면, 이 창구로 흉내 내지 말고 그렇다고 말한다. `core:read` 토큰은 `/api/core`
아래만 읽는다 — 다른 길은 공개 측과 따로 정한다.

| 원하는 것 | 이 창구 | 어디서 |
| --- | --- | --- |
| 지난 · 앞으로의 기간의 선 | 오늘 유효한 선만 온다 | 공개 측의 관계 내보내기 · 묶음(기간을 가리지 않고 전부 싣는다 — 더 넓은 토큰이 든다). 공개 측이 0.4.78 이상이면 이 창구의 `shape=sp` 도 있다 — 선이 쌍마다 기간 목록(`periods`)으로 와서 받는 모양이 다르다(형제 SP 가 쓰는 모양, 시험장에는 없다) |
| 수량을 경로 따라 곱한 전개 표 | 선마다의 수량만 온다 | 층 2 가 계산하거나(§6.2) SP 화면에서 본다 |
| 계보의 낡음(원천이 바뀌어 파생물이 낡았나) | 안 온다 | SP 안의 판정이다 — SP 화면에서 본다. 이 플랫폼에서 지어 판정하지 않는다 |
| 제안된 관계(확정 전) | 안 온다 | 사람이 SP 에서 확정하면 그때 보통의 선으로 온다 |
| 첨부 파일 | 안 온다 | — |
| 공개 안 된 타입, 그쪽으로 가는 선 · 참조의 상대 | 안 온다 | 공개 측 화면 「코어 현황 › 제외된 관계」 가 무엇이 왜 빠지는지 말한다. 기대한 관계가 안 오면 공개 측에 그것을 봐 달라고 한다 |
| 바뀐 순간의 알림 | 주기로 물어야 안다 | 공개 측의 웹훅(선택) — 아래 |

**웹훅을 붙일 때.** 공개 측 관리자가 이 플랫폼의 수신 주소 · 서명 비밀을 SP 에 적고 「코어 공개 타입만」
을 켠다. 신호에는 **값이 없다** — 받으면 서명(`X-Signature-256` = `sha256=` + HMAC-SHA256(비밀, 원문
바이트))을 상수 시간 비교로 확인하고, 2xx 를 바로 돌려준 뒤, 그 타입의 받기를 한 번 돌린다(§5.1 의
잠금 · 규칙 그대로 — 층 1 이 둘이 되면 안 된다). 그 타입은 `target.type_slug` 다(선의 신호면 출발 객체의
타입, `ontology.*` 면 카탈로그부터 전부). 같은 신호가 두 번 올 수 있으니 `X-Delivery-Id` 로
거른다. 신호로 값을 반영하지 않고, **주기 실행은 끄지 않는다**(웹훅은 세 번 시도한 뒤 멈춘다).

## 6. 반영 (층 2)

### 6.1 객체

- **입력은 사본 표뿐이다.** 기준정보가 수만 건 이하면 **매번 전체 대조**가 가장 단순하고 틀릴 일이
  적다. 더 크면 `changed_at` 이 지난 반영보다 나중인 행만 읽는다.
- 이 플랫폼의 레코드에 **SP key 를 담는 칸**(예: `sp_type`, `sp_key`)을 둔다. 둘을 잇는 유일한 끈이다.
  이름으로 잇지 않는다. 이미 있던 레코드와 처음 잇는 것은 사람이 정한 대로(§2-8).
- 식별자가 바뀌면 **같은 레코드**의 SP key 만 바꾼다(사본의 `sp_core_previous_key` 로 안다). 새 레코드를
  만들지 않는다.
- **매핑은 사람이 정한 대로**(§2-3). 정해지지 않은 칸은 넣지 않는다.
- **참조 칸**(`object_ref`)의 값은 상대의 SP key 다. 대상 타입을 먼저 반영한다. 이 플랫폼에서 못
  찾으면 `sp_core_previous_key` 로 새 key 를 풀어 다시 찾는다. 그래도 없으면 **보류**하고 다음 반영에서
  다시 푼다. 빈 레코드를 지어 만들지 않는다.
- **사라진 것**은 사람이 정한 대로(§2-4). 다른 기록이 가리키는 레코드는 지우지 않는다.
  `merged_into` 가 있으면, 정한 대로 이 플랫폼의 참조를 이긴 쪽으로 옮긴다.
- **SP 와 이 플랫폼의 값이 다를 때**는 사람이 정한 대로(§2-5).
- 사람이 이 플랫폼에서 만든 레코드(SP key 가 없는 것)는 지우거나 바꾸지 않는다 — §2-4 에서 정한
  합침의 참조 옮기기만 예외다.

### 6.2 선

- **객체를 먼저 반영한다.** 선의 끝은 객체 레코드다.
- 입력은 사본의 **이어진 선**이다. 매핑을 정한 관계 종류만 넣는다(§2-3). 정의 판이 바뀌어 새로 열린
  종류는 넣지 않고, 실행 기록의 알림으로 사람에게 보인다.
- **끝 찾기.** 출발은 (`src_type`, `src`), 도착은 (`dst_type`, `dst`) 의 SP key 로 이 플랫폼의 레코드를
  찾는다. 어느 표에서 찾을지는 **`dst_type` 이 정한다** — 끝이 인터페이스인 종류는 선마다 다르고, 같은
  key 가 두 표에 있을 수 있다. 못 찾으면 `sp_core_previous_key` 로 풀고, 그래도 없으면 **보류**한다(끝
  레코드를 지어 만들지 않는다).
- **연결은 이 플랫폼의 레코드를 가리키게 둔다.** SP key 를 연결에 복사해 두면 식별자가 바뀔 때마다
  연결을 끊었다 다시 만들게 된다. 레코드를 가리키면 key 가 바뀌어도(객체 반영이 레코드의 SP key 만
  바꾼다) 연결은 그대로다.
- **SP 에서 온 연결에는 표시를 둔다**(출처 칸 등). 대조는 다섯 칸으로 한다 — 사본의 이어진 선과, 표시가
  있는 연결의 두 끝 레코드에서 만든 다섯 칸을 맞춰 더하고 끊는다. **끊는 것은 표시가 있는 연결뿐이다** —
  사람이 이 플랫폼에서 이은 연결은 SP 에 없어도 그대로 둔다. 끊은 연결을 지울지 「끊김」 으로 남길지는
  이 플랫폼의 관례를 따른다. 사람이 이은 연결의 끝이 **합쳐져** 사라졌으면 §2-4 의 답(참조를 이긴 쪽으로
  옮기나)을 그대로 따른다.
- 선의 칸(`properties`)은 객체처럼 **통째로 바꾼다.** `evidence_note` 는 근거 메모다 — 보일지는 매핑대로.
- **선의 뜻은 카탈로그에서 읽는다**(사본의 최신 카탈로그, 종류마다 — §5.2). 칸 이름을 코드에 박지 않는다
  — 설치마다 다르다.
  - **수량** — `quantity_key` 가 비어 있지 않으면 `properties[quantity_key]` 가 그 선의 수량이다. 칸이
    없거나 숫자가 아니면 **1**, 0 은 0 이다(SP 의 전개와 같은 뜻). 전개를 하면 경로를 따라 곱하고, 한
    경로에 같은 레코드가 두 번 나오면(순환) 멈추고 알린다.
  - **계보** — `lineage_source` 가 `src` 면 출발이 원천, `dst` 면 도착이 원천이다. 다른 끝이 파생물이다.
    「무엇에서 만들어졌나」 는 파생물에서 원천 쪽으로 읽는다. 낡음은 오지 않는다(§5.7).
  - **유효 기간** — 사본에 `valid_from` · `valid_to` 를 둔 경우만 보일 수 있다(§4). 이 플랫폼에서 기간으로
    다시 거르지 않는다 — 오늘 유효한 선만 오고, 끝나는 날 끊김이 온다.

## 7. 화면과 운영

- **관리 화면**(관리자만, 화면이 없는 플랫폼이면 같은 것을 관리 API 로): 지금 받기 · 처음부터 다시 받기(확인 대화상자) · 강제 정리(「절반 넘게 안
  옴」 을 사람이 확인한 뒤에만) · 마지막 실행 결과와 확인 필요 사유 · 최근 실행 목록 · 타입별 건수 · 정의 판.
- **주기 실행**은 이 플랫폼의 스케줄러로 한다. 실패해도 다음 주기가 이어 받는다(기준 시각이 마지막
  성공 위치에 있으므로).
- **토큰**은 로그 · 화면 · 오류 메시지에 찍지 않는다.
- 요청 시간 제한은 60초, 한 쪽 크기는 500.

## 8. 시험장으로 확인하기

```bash
python testbed/fake_sp.py              # 다른 창에서. http://127.0.0.1:8765/api · 토큰 test-token
```

(`python` 이 없는 환경이면 `python3`. 포트가 겹치면 `--port` 로 바꾸고 채점기에 `--server http://127.0.0.1:<포트>`
를 준다 — 채점기의 기본은 8765 다.)

단계마다 이렇게 한다.

1. `curl -X POST http://127.0.0.1:8765/_step` — 이번 단계의 설명이 온다. `title`, `what_happened`,
   `run`(보통 · 처음부터), `expect_status`(정상 · 확인 필요), `rules`(§5.6 번호)가 들어 있다.
2. 이 플랫폼의 받기를 한 번 실행한다(`run` 이 「처음부터」 면 처음부터 다시 받기로).
3. 사본을 JSON 으로 내보낸다. 모양은 `testbed/compare.py` 머리말에 있다 — 객체는 비활성까지 전부
   (`active` 로 가른다), 선은 지금 이어진 것만. 내보내기는 시험용 명령이나 함수로 만든다.
4. `python testbed/compare.py --dump state.json` — 「N단계 통과」 가 나와야 한다. 불통이면 어디가
   왜 다른지와 규칙 번호를 찍는다.
5. 실행 결과의 상태가 `expect_status` 와 같은지 본다.

| 단계 | 일어나는 일 | 결과 상태 |
| --- | --- | --- |
| 1 | 첫 적재 — 한 쪽에 2건씩이라 여러 쪽 | 정상 |
| 2 | 고침 · 칸 비움 · 사용 중지 · 지움 · 합침 · 선 끊음 | 정상 |
| 3 | 식별자 두 번 바뀜 · 안 보이게 됨 · 선을 남긴 삭제 | 정상 |
| 4 | 되살림 · 여러 쪽 · 커서 오류(-CORE-0002) | 정상 |
| 5 | 오래 안 받음 — 선이 `reset` | 정상 |
| 6 | 정의 판 바뀜 — 타입 공개(예전 선이 생김), 인터페이스 끝 | 정상 |
| 7 | 공개 거둠 — 그 타입만 -CORE-0001 | 확인 필요 |
| 8 | 토큰 범위 줄어듦 — 처음부터 다시 받기, 절반 넘게 안 옴 | 확인 필요 |

**8단계를 모두 통과해야 한다.** 처음부터 다시 하려면 `curl -X POST http://127.0.0.1:8765/_restart` 를 하고
사본 · 기준 시각을 비운다.

**자동 시험으로 만든다.** 이 저장소의 시험이 가짜 SP 를 띄우고 8단계를 돈다.

- 띄우기: `python3 -B testbed/fake_sp.py --port 0 --quiet` — 빈 포트를 잡고 **첫 줄에 `PORT=<번호>`** 를
  찍는다. 시험이 그 줄을 읽어 주소를 만든다. 파이썬 시험이면 `fake_sp.serve(0)` 를 불러 스레드로
  돌려도 된다(`server.server_address[1]` 이 포트).
- `-B` 를 붙인다 — 안 붙이면 이 폴더에 `__pycache__` 가 생긴다. 이 폴더는 고치지 않는다.
- 단계마다 `POST /_step` → 받기(층 1 · 층 2) → 내보내기 → `python3 -B testbed/compare.py --dump … --server …`
  의 끝나는 값이 0 인지, 실행 결과 상태가 `expect_status` 와 같은지 본다. 끝나면 서버를 끈다.
- 층 2 는 아래 §8.1 의 확인표를 이 플랫폼의 말로 옮겨 단정한다.

### 8.1 층 2 확인표 — 시험장 단계 뒤 이 플랫폼의 표

채점기는 층 1(사본)만 본다. 층 2 는 매핑이 플랫폼마다 달라 정답을 대신 줄 수 없으므로, **SP key 로
적은** 아래 결과를 이 플랫폼의 표로 옮겨 시험에 넣는다(시험장의 `vendor` · `part` 를 이 플랫폼의 어떤
표에 넣을지는 시험에서만 정한다).

| 단계 뒤 | 이 플랫폼의 표가 이래야 한다 |
| --- | --- |
| 1 | 살아 있는 SP 객체마다 레코드가 **하나씩**, SP key 가 채워져 있다. P-1 ~ P-5 의 공급사 참조가 V-1 ~ V-5 의 레코드를 가리킨다. 사람이 만든 레코드는 그대로다 |
| 2 | V-1 의 이름이 「ACME Korea」. V-4 는 그만 씀(정한 대로). V-5 · V-3 은 사라짐 — 지워지지 않았다. P-3 의 참조는 V-1 레코드(합침). P-5 의 참조는 비었다(SP 가 비웠다). P-4 의 꼬리표는 비었다. V-6 · P-6 이 새로 있다 |
| 3 | V-2 였던 레코드가 **같은 레코드 그대로** key 만 V-2b — 새 레코드가 생기지 않았고 P-2 는 여전히 그것을 가리킨다. P-1 이던 레코드도 같은 레코드로 P-1X. V-6 은 사라짐 — 이름 · 칸이 그대로다. P-4 는 사라짐 |
| 4 | V-5 레코드가 다시 쓰임(같은 SP key 라 예전 레코드가 되살아난다) · 이름 「미래(재등록)」, P-5 가 그것을 가리킨다. P-10 ~ P-21 이 새로 있다 |

**선** — `supplied_by`(공급처) · `inspected_by`(검사처)를 이 플랫폼의 연결로 넣는다고 정했을 때다(시험에서만
정한다). 시험을 시작할 때 **사람이 이은 연결** 하나(예: P-2 – V-4)를 만들어 두고, 모든 단계 뒤에 그대로인지도
본다.

| 단계 뒤 | 이 플랫폼의 연결이 이래야 한다 |
| --- | --- |
| 1 | 공급처 7개 — P-1–V-1(칸 `n`=3) · P-1–V-3 · P-2–V-2 · P-3–V-3 · P-4–V-4 · P-5–V-5 · P-5–V-2. 검사처는 P-1–K-1 하나로, **공급사 쪽** K-1 레코드에 이어져 있다. 공장 쪽 K-1 과 생산지(`made_at`) 연결은 없다(`plant` 미공개) |
| 2 | P-1–V-3 이 없다(합침 — P-1–V-1 과 겹쳤다). P-3 은 V-1 레코드에 이어져 있다. P-5 의 연결이 없다(V-5 지움 · P-5–V-2 끊음). P-6–V-6 이 있다 |
| 3 | P-2 의 연결이 **같은 레코드**(V-2 였던 V-2b)에 그대로 있다 — 끊겼다 다시 생기지 않았다. P-1X(P-1 이던 레코드)의 연결 둘도 그대로다. P-4–V-4 · P-6–V-6 이 없다(P-4 지움 · V-6 안 보임) |
| 4 | P-5–V-5 가 다시 있다(되살아난 V-5 레코드). P-10 ~ P-21 의 공급처 연결 12개 |
| 5 | P-3–V-1 이 없다(끊긴 기록이 정리돼 `reset` 으로 처음부터 받고서야 안다) · P-10–V-2b 도 없다(P-10 지움) |
| 6 | (`plant` 를 넣는다고 정했으면) 생산지 P-1X–PL-1 · P-2–PL-1, 그리고 검사처 P-1X–K-1 이 **공장 쪽** K-1 레코드에 하나 더 — 공급사 쪽 것과 둘이다 |
| 8 | 6단계 뒤와 같다 — 층 1 이 정리를 멈췄으니 연결도 끊지 않는다 |

참고 구현으로 시험장을 돌려 보면 무엇이 정답인지 볼 수 있다.

```bash
python testbed/fake_sp.py &
printf '[sp]\nbase_url = http://127.0.0.1:8765/api\ntoken = test-token\nout_dir = out-testbed\n' > testbed.ini
curl -s -X POST http://127.0.0.1:8765/_step
python sp_core_pull.py --config testbed.ini            # 8단계는 --full

```

박지 않는다. 시험장은 실제 SP 와 같은 모양으로 답한다.

## 9. 하지 말 것 — 실제로 있었던 실수

- `since` 를 자기 시계로 만든다 → 몇 초 차이로 변경이 샌다.
- 처음부터 받기 전에 표를 비운다 → 도중에 실패하면 데이터가 사라진다.
- 404 를 상태 코드만 보고 「타입 없음」 으로 처리한다 → 커서 문제 하나로 수신 전체가 멈춘다.
- 선을 (`src`, `relation`, `dst`) 셋으로만 가린다 → 인터페이스 끝에서 선이 겹쳐 사라진다.
- `properties` 를 기존 값에 합친다 → SP 에서 비운 칸이 안 지워진다.
- `hidden` 행으로 이름 · 칸을 덮는다 → 가진 이름이 식별자로 바뀌고 칸이 빈다.
- `renamed_from` 을 무시한다 → 같은 것이 옛 key · 새 key 두 줄로 남는다.
- 지운 객체의 선을 SP 가 「끊긴 선」 으로 줄 것이라고 기다린다 → 안 온다(§5.4-6).
- 끝 슬래시(`/api/core/`)를 붙이고 307 을 안 따라간다 → 「창구가 없다」 로 보인다(지금은 둘 다 된다).
- 토큰을 저장소에 커밋하거나 로그에 찍는다.
- 끝이 인터페이스인 선의 도착을 `dst` 만으로 찾는다 → 같은 key 가 두 표에 있어 엉뚱한 레코드에 잇는다.
- 연결에 SP key 를 복사해 두고 그것으로 잇는다 → 식별자가 바뀔 때마다 연결이 끊겼다 다시 생긴다.
- SP 에 없는 연결을 모두 끊는다 → 사람이 이 플랫폼에서 이은 연결까지 사라진다.
- 수량 칸 이름(`qty` 등)을 코드에 박는다 → 설치마다 다르다. 카탈로그의 `quantity_key` 가 정본이다.

## 10. 끝나면 사람에게 보고한다

1. 만든 것 — 파일 · 표 · 화면 위치 · 스케줄 설정.
2. 매핑 표 — SP 타입 · 칸 → 이 플랫폼의 표 · 칸, SP 관계 종류 → 이 플랫폼의 연결(수량 · 계보 · 유효
   기간을 쓰는지). 사라진 것 처리 · 값 충돌 처리.
3. 시험장 8단계 결과 — 단계마다 통과 여부와 결과 상태.
4. 실제 SP 연결 점검 결과 — 카탈로그의 `system` · `revision` · 타입 수, 첫 수신 건수.
5. 남은 결정 · 확인할 것.
